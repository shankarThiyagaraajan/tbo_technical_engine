## What changed
Kit 3 and the test profile (remove-lab-mode row D2-5, plan D2, P1, P18, P19, P22, P27, P28): `tbo-platform-kit` moves from `~=2.5` (tbo_platform `8df4ffc`, kit 2.5.0) to `~=3.0,>=3.0.1` at `d238cc07cf34af2d33e760a512df3eae007aefa0` (kit 3.0.1, which ends its own migration guard's transaction so an `autocommit_block` migration runs on the test profile), and `tbo-signals` from 0.6.0 to 0.8.0 at tbo_platform_kit `2bf19d70f5f293b5cdaa7da2db2544d4ac32fb4c`; `uv.lock` changes only those two. tbo_contracts stays at 1.30.0 (`f884a2d`); no `.v2`.
1. Mode: kit 3 knows `paper` and `live` only. An unset, empty, `lab` or unknown `TBO_MODE` stops the API, the signal worker, Celery (worker and beat) and Alembic at start with the plan's words (P2; proved for each entry point by a test). A deployment that still sets `TBO_MODE=lab` stops; paper and live are unchanged.
2. Signals: `services/platform_signals.py` passes the profile's `signals_default` to `resolve_level(default=)` and its stream prefix to `stream_name` and `Signals`; in paper and live the level and the stream are what they were (`paper.signals.v1`, `live.signals.v1`).
3. Tests: they run on the kit's test profile; `tests/conftest.py` carries the P18 lock; nothing sets `TBO_MODE=lab`; Alembic in the tests runs as plain `alembic` through the kit's runner (`python -m tbo_platform_kit.testing.run alembic upgrade head`), whose guard refuses a database that is not a test database; every TRUNCATE, DROP, DELETE FROM and flush in `tests/` and `scripts/` is behind the matching kit guard on its own connection; AST-based static tests pin that, no child process getting paper or live, no test setting `TBO_MODE` outside a `tbo_real_mode` test, and no `src/` module importing `tbo_platform_kit.testing`.
4. `scripts/benchmark.py live` (P22): reads `TBO_TEST_DATABASE_URL` and `TBO_TEST_REDIS_URL` only, runs only on the test profile (`uv run python -m tbo_platform_kit.testing.run scripts.benchmark live ...`), refuses a database that is not `tbo_test_<x>` with the comment `tbo-test`, and a Redis that holds a `paper.*` or `live.*` key.
5. `compose.dev.yml` (P27): PostgreSQL is `tbo_test_dev` with an init script (`compose.dev/init/10-test-database.sql`) that writes the `tbo-test` comment and creates `tbo_dev`; an old dev container needs `docker compose -f compose.dev.yml down -v`, then `up -d --wait`. Dev only; the image and the stack do not use it.

## Why
Remove-lab-mode plan, wave 4: lab mode is removed from the TBO platform, every service moves to kit 3 and its tests stop depending on a lab mode; `scripts/benchmark.py live` must never reach a real database or Redis.
